Candidate 03

One unit of work for player mutation

Strong ports & adapters

backend/internal/handlers (104 files with .Begin) · internal/services/inventory_service.go · player_service.go · services/occ_retry.go · pkg/auditlog · internal/worker

Before — atomicity by convention

sequenceDiagram

    participant D as Postgres
    H->>D: DELETE player_killer_moves
    H->>D: audit log via db.DB
    H->>D: SELECT combat_settings
    H->>D: UPDATE players

The same shape appears in registration, achievements, buyback payouts and combat finalize.

After — one transaction seam

sequenceDiagram
    participant H as Handler
    participant U as Unit of work
    participant D as Postgres
    H->>U: intent plus mutation
    U->>D: BEGIN lock player timeouts
    U->>D: handles bound to the tx
    U->>D: version check then COMMIT
    U-->>H: typed result
    U->>H: after-commit effects
inventory Gu progress audit lock order OCC retry

Problem

Handlers open 238 transactions by hand, multi-table writes split across autocommit statements, and the optimistic-concurrency helper has no caller — atomicity is a convention, not a guarantee.

Solution

One unit-of-work module owns begin, lock order, timeouts, tx-bound inventory/Gu/progress/audit handles, the version check and commit, then runs after-commit effects; callers express a mutation, not a transaction.

Already written down: docs/PLAYER_PERSISTENCE_OPTIMIZATION_PLAN.md argues field ownership, lock order and an outbox. This candidate is the module that makes those rules enforceable — it does not contradict the plan.

Top recommendation

Player snapshot

Every hot feature — combat, movement, arena, scouting, admin — crosses the player row, so one read module with typed views pays back at 122 call sites and is the prerequisite for the unit of work and for the first player-state test that does not need Postgres.

Open candidate 02

Cheap prerequisite: candidate 01. Its deletion removes the second damage rule before the snapshot work starts touching combat call sites.
