# Turn-Based Combat Inventory

Context: Wayfinder map [Chuyển toàn bộ combat sang turnbase có điều khiển](https://github.com/VipPro67/GuWorld/issues/386), research ticket [Kiểm kê nền turnbase auto và các mode combat hiện có](https://github.com/VipPro67/GuWorld/issues/387).

This report describes the repository at the branch base commit. It is an inventory for design decisions, not an implementation proposal.

## Current combat loop

- The main combat API is `POST /api/combat/start`, which takes a `simulator.CombatLoadout`. The handler requires an already initialized `player.ActiveCombat`, calls `ResolveCombat`, commits all outcome changes, publishes combat-ended, then returns winner, full logs and combatant data. A single request therefore resolves the full encounter; it does not pause for a player command. Sources: [server routes](../../backend/internal/server/server.go#L787-L799), [AutoCombatStart](../../backend/internal/handlers/combat_auto.go#L27-L30), [handler flow](../../backend/internal/handlers/combat_auto.go#L55-L60), [resolve and commit](../../backend/internal/handlers/combat_auto.go#L96-L145).
- `ResolveCombat` builds a simulator state, enables turn snapshots, calls `simulator.Simulate` to completion, then consumes resources, evaluates victory/defeat, settles rewards/persistence and queues post-commit effects. `CombatResolution` packages the final result, not a pending command state. Sources: [resolution and simulator call](../../backend/internal/handlers/combat_auto_resolve.go#L47-L85), [snapshot and simulation](../../backend/internal/handlers/combat_auto_resolve.go#L143-L155), [settlement](../../backend/internal/handlers/combat_auto_resolve.go#L162-L165), [finalize](../../backend/internal/handlers/combat_auto_resolve.go#L293-L308).
- The simulator has a turn loop capped at 100 turns. It applies start-of-turn effects, sorts every living combatant by `EffectiveSpeed` descending, then automatically executes that combatant's precomputed actions in sequence. Speed therefore orders actors within each turn; code does not use speed to give one actor multiple turns in a continuous time queue. Actions are ordered by authored tactic priority/category, not chosen interactively during a turn. Sources: [Simulate setup and fixed cap](../../backend/internal/simulator/engine.go#L1094-L1105), [action priority sorting](../../backend/internal/simulator/engine.go#L1165-L1209), [speed ordering](../../backend/internal/simulator/engine.go#L1561-L1568), [automatic actor action loop](../../backend/internal/simulator/engine.go#L5456-L5476).
- Turn snapshots are captured for replay, but the browser receives the finished log after the simulation. The client calls `/api/combat/start`, stores all logs in `activeCombatReplay`, and later animates them; this is visual replay rather than command input. Sources: [snapshot capture before Simulate](../../backend/internal/handlers/combat_auto_resolve.go#L143-L145), [client request/replay](../../frontend/src/store/slices/combatSlice.ts#L38-L61).
- The simulator itself is usable by NPCs and players: `CombatState` accepts `Allies` and `Enemies`; each `CombatantAuto` has stats, speed, action list, mechanics, tactics and consumable resource state. `buildSimCombatState` loads the initiator, party members/pets/variant NPCs, then enemies/defenders. Sources: [state builder](../../backend/internal/handlers/combat_sim_build.go#L18-L26), [allied actor construction](../../backend/internal/handlers/combat_sim_build.go#L28-L89), [enemy construction](../../backend/internal/handlers/combat_sim_build.go#L91-L103).

## Loadouts, tactics and auto behavior

- For the initiating player, a submitted loadout's Gu IDs select which Gu become actions; otherwise saved Gu priority settings are used, falling back to all equipped active Gu. Passive mechanics still come from all equipped active fed Gu. Basic attack is added as a fallback action. Sources: [loadout selection](../../backend/internal/handlers/combat_auto.go#L855-L897), [selected Gu action construction](../../backend/internal/handlers/combat_auto.go#L915-L929), [basic attack and tactics](../../backend/internal/handlers/combat_auto.go#L1055-L1095).
- `CombatSettings` persist Gu priorities/conditions, killer-move priorities, category priorities and auto-heal/mana settings. The simulator applies them automatically; `CombatSlice.executeAutoCombat` sends the current loadout and there is no per-turn submit-command method in this slice. Sources: [settings read/write](../../backend/internal/handlers/combat_settings.go#L11-L58), [CombatSlice API surface](../../frontend/src/store/slices/combatSlice.ts#L8-L35), [executeAutoCombat](../../frontend/src/store/slices/combatSlice.ts#L38-L45).
- NPC tactics have two historical patterns: `BuildEnemyActions` chooses a profile-based policy (`boss_burst`, `defensive`, `boss_balanced`, default first affordable action), while the current `CombatAuto` simulator receives precomputed action lists and automatically runs qualifying actions. Treat the older handler helper as evidence of existing AI vocabulary, not proof that every current encounter path uses it. Sources: [BuildEnemyActions](../../backend/internal/handlers/combat_ai.go#L11-L47), [AI profile policies](../../backend/internal/handlers/combat_ai.go#L115-L180).
- Auto combat currently can execute several actions for one actor in a turn (e.g. shield/support and attacks), subject to conditions/resources; the user-facing idea of choosing “one Gu per turn” is a different action economy that needs an explicit decision before reuse. Source: [sequential combatant action loop](../../backend/internal/simulator/engine.go#L5456-L5476).

## Current PvP and persistence seams

- Open-world PvP is started through the map movement handler when `attackTargetID` is supplied. Existing eligibility checks require a recently active target, same map instance/world-map and, when parties apply, a different party; the attack also has an attack-range check in the handler. The encounter captures defender stats, Gu inventory/settings and target ID. This differs from the desired immediate pull without acceptance, so range/eligibility are open product decisions. Sources: [target query](../../backend/internal/handlers/exploration_move.go#L291-L310), [range branch and PVP snapshot](../../backend/internal/handlers/exploration_move.go#L410-L440).
- The initiated encounter is initialized by `StartCombat` and persisted into the initiating player's `active_combat` as part of the movement write path. In `ResolveCombat`, a PvP defender may be reloaded from the database and rebuilt through the same combatant builder as the attacker rather than submitting a command. Sources: [StartCombat in movement flow](../../backend/internal/handlers/exploration_move.go#L723-L725), [combat state identity/owner](../../backend/internal/handlers/combat_state.go#L24-L45), [defender rebuild](../../backend/internal/handlers/combat_sim_build.go#L295-L329).
- Combat state is currently a durable JSON domain object embedded in player state; it stores encounter identity, enemy data, allies/enemies, settings, status and encounter context. Player events publish `combat.started` / `combat.ended` with active combat state. These are existing seams for an interactive-session design, but no current per-turn pending actor/command/deadline/session ownership was found in this path. Sources: [CombatState fields](../../backend/internal/models/legacy_combat.go#L24-L96), [combat event names/payload](../../backend/internal/handlers/player_events.go#L42-L54).
- Existing `/api/combat/flee/:id` is a standalone combat mutation endpoint, separate from a turn command. Client treats a successful flee as clearing active combat. Integrating flee into a speed-ordered command requires a new contract. Sources: [flee route](../../backend/internal/server/server.go#L793-L798), [flee client behavior](../../frontend/src/store/slices/combatSlice.ts#L86-L96).

## Implications for next decisions

1. Preserve the existing deterministic simulator as a rules/action resolver where practical, but the current `Simulate(state) -> complete log` boundary does not expose “resolve one player-selected action and persist pending session” directly.
2. “Speed-based turns” should specify whether it means reordering actors each round (current behavior) or continuous initiative / extra actions (a change). Current speed already incorporates effective-speed status and first-turn priority mechanics.
3. Decide whether a player turn means one selected action, one selected Gu plus passive start/end effects, or a batch compatible with current auto tactics. Current combat can execute multiple actions from a loadout in the same actor turn.
4. NPC auto policy can reuse saved tactical conditions or the existing AI profile vocabulary, but identify which behavior belongs to current builders before treating `BuildEnemyActions` as authoritative.
5. Interactive PvP needs a two-participant session/command contract. The current world attack is range gated, attacker-owned and server-resolved; existing SSE player combat events provide a notification pattern but not a turn protocol.
6. Inventory required before migration decisions: locate every producer/caller of `ResolveCombat`, since arena workers and gameplay settlement paths may want to remain auto-resolved even if player-facing encounters become interactive.
