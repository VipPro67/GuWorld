1. Break the God Store into domain slices

Strong in-process
frontend/src/store/useGameStore.ts (7,971 lines)

Before

After

Problem: 100+ state fields, 120+ methods, 8 WS channels — all in one module. Every consumer imports the full store. Interface is nearly as wide as the implementation (shallow).

Solution: Slice into domain stores (combat, inventory, sect, aperture, auth, trade) that each own their state and actions. Shared utilities (authFetch, dictionaries, WS subscriptions) live in a thin coordination layer.

  • leverage: one combatStore serves combat components, not 7,971 lines of mixed concerns
  • locality: combat bugs live in combatStore, not scattered across 120 methods
  • testability: each slice testable in isolation with minimal mock state
  • deletion test: deleting combatStore would force combat logic back into every component — earns its keep

2. Collapse fat handlers into domain modules

Strong in-process
backend/internal/handlers/player.go (5,511 lines) · admin.go (4,442) · sect.go (3,891) · combat_*.go (~9,300 total)

Before

After

Problem: player.go has 36 exported + 28 unexported functions covering auth, inventory, combat, cultivation, stats, and profile. Admin.go covers 10+ domains with 70 CRUD functions. Cross-file coupling via unexported evaluateManaTxEquipped (called from combat_auto, combat_auto_resolve, tribulation).

Solution: Extract domain modules (player, inventory, combat, sect, aperture, admin) each with a small interface. Shared helpers (evaluateMana, responseWithPlayer, transaction patterns) become module-internal or shared utilities. Handlers become thin HTTP adapters calling domain methods.

  • locality: combat bugs live in combat module, not scattered across 17 files + player.go
  • leverage: one evaluateMana module serves all callers through a clean seam
  • testability: domain modules testable without HTTP; handlers testable with mocked domain
  • deletion test: deleting player module would force 36 handlers to inline 5,511 lines — earns its keep

3. Eliminate unexported cross-file coupling

Strong in-process
evaluateManaTxEquipped · responseWithPlayer* · enemyPathResistance

Before

After

Problem: evaluateManaTxEquipped is defined in player.go but called from combat_auto.go, combat_auto_resolve.go, and tribulation.go. Changing its signature silently breaks three files. No seam exists — can't mock for tests or swap implementations.

Solution: Extract to an exported module (mana or combat/mana) with a clean interface. Same for responseWithPlayer* helpers and enemyPathResistance. Two adapters (real DB + test mock) justify the seam.

  • locality: mana logic changes don't ripple across 3+ files
  • leverage: one mana module serves all combat/cultivation callers
  • testability: mock the mana seam in combat tests without touching player.go
  • deletion test: deleting would force 3 files to inline ~200 lines of mana math

4. Consolidate duplicated auth/fetch utilities

Worth exploring in-process

Before

After

Problem: getCookie() is identical in both stores. authHeaders() in useWorldStore reimplements what authFetch() does in useGameStore. ToastMessage interface is declared twice. Cell cache merge logic is near-identical across two methods.

Solution: Extract lib/auth.ts with shared getCookie, authFetch, authHeaders. Extract lib/types.ts for shared interfaces. Merge duplicate cell cache logic.

  • locality: auth changes in one place, not two
  • leverage: one authFetch serves all stores
  • deletion test: deleting would force each store to reimplement token + CSRF logic

5. Unify data-driven game data (hardcoded → CSV)

Worth exploring in-process

Current state

After

Problem: Gu/Item/Monster/Constitution/Race data is CSV-driven via Admin import. But aperture ResourceNodeTemplates (15 node types with costs, production, defense) and disposable email blocklist (~350 domains) are hardcoded in Go. Changing aperture balance requires code deploy.

Solution: Move ResourceNodeTemplates to a CSV table (aperture_node_templates) loaded into a registry at startup, following the same pattern as Gu/Item registries. Move disposable email list to a DB table or config file.

  • leverage: balance designers edit CSV, not Go code
  • deletion test: deleting hardcoded templates would force inline data in handlers — moves in wrong direction

6. Separate workers from handler files

Worth exploring in-process
handlers/tribulation.go · handlers/arena_worker.go · handlers/death_arena_worker.go

Before

After

Problem: tribulation.go (2,315 lines) mixes HTTP handlers with background worker goroutines in the same file. Arena and death-arena workers follow the same pattern. Worker logic shares globals and DB access patterns with handlers, making it hard to reason about concurrency boundaries.

Solution: Move worker goroutines to worker/ package files, keeping handlers as HTTP-only adapters. Workers share domain logic through exported module functions, not package-level globals.

  • locality: background logic separated from request-response logic
  • testability: workers testable without HTTP context
  • deletion test: deleting would mix worker goroutines into handler files — wrong direction

Top recommendation

#1 Break the God Store into domain slices

The 7,971-line useGameStore is the single biggest friction point. It couples every frontend component to 100+ state fields and 120+ API methods. Slicing it into domain stores (combat, inventory, sect, aperture, auth, trade) with a shared authFetch/dictionaries layer would:

  • Shrink each module to ~150-250 lines (deep, not shallow)
  • Eliminate the global actionLoading debounce lock
  • Make each domain testable with minimal mock state
  • Remove 3 instances of copy-pasted auth utilities
  • Enable targeted optimistic updates per domain

Start with combatStore (most complex state + WS subscriptions) as the pilot, then extract inventoryStore (most duplicated API calls). The pattern established by these two will guide the rest.
