Architecture Review

GuWorld - Codebase Architecture Deepening

Shallow Modules Testability Gap Leaky Interfaces

Candidate Deepening Opportunities

Collapse the Player Auth Pipeline

The player registration and authorization handlers are among the largest in the codebase (200–500+ lines each). While their public interface is a simple gin endpoint, the implementation mixes HTTP handling, database transactions, password hashing, and gameplay logic—all intertwined. There are no internal seams, and the deletion test confirms that removing any handler would scatter complexity into other files (e.g., moving registration logic into models or db).

Problem

The handlers are shallow in interface (tiny gin function) but deep in implementation (mixed HTTP, DB, and game logic). This violates the principle that the interface should be small and stable while the implementation can evolve independently. Without internal seams, debugging and testing require stepping through dozens of lines in a single file.

Solution

Extract validation, database access, and gameplay logic into separate modules behind a single seam. Introduce an adapter for the HTTP layer so tests can mock the handler interface directly. This creates a deep module with a small, stable interface (the gin endpoint) and concentrated implementation behind a seam.

Wins

  • Tests hit one interface (the gin endpoint) rather than scattering across 200+ lines.
  • Bugs concentrate in one module, improving maintainability.
  • Leverage increases: the same validation and DB logic can be reused across auth, login, and registration flows.

Recommendation

Strong Deepen the player auth pipeline by extracting validation, DB access, and gameplay logic into testable modules behind a single seam.

Deepen Frontend Store Slices

Each of the 22 Zustand slices combines state management, API calls, and cross‑cutting concerns (toasts, logs, event subscriptions). This leaks responsibilities across interfaces, making tests require network mocking and state synchronization. The deletion test shows that removing a slice would force related logic into other slices, increasing coupling.

Problem

Cross‑cutting concerns (addToast, addLog, subscribePlayerEvents) are embedded in every slice’s interface, violating the principle of localized interfaces. Each slice becomes a “fat” module where state, API, and side‑effects are entangled.

Solution

Extract cross‑cutting concerns into shared adapters (e.g., a NotificationAdapter, LogAdapter) and define clear seams between state management and API access. This yields shallow, testable slices where each interface exposes only its domain responsibility.

Wins

  • Interfaces become focused on a single domain (e.g., authSlice handles auth only).
  • Cross‑cutting concerns are centralized, reducing duplication.
  • Localizability improves: changes to logging or toasting affect one adapter, not twenty slices.

Recommendation

Strong Restructure the frontend store slices by extracting cross‑cutting concerns into reusable adapters and defining clear seams between state and API.

Deepen the Combat Module

The combat system spans ~6,256 lines across 20+ files (combat.go, combat_sim_build.go, combat_auto.go, etc.). The interface is fragmented across many exported functions, and core logic (damage, AI, loot) lacks unit tests. Integration tests dominate, leaving gaps in deterministic testing.

Problem

Multiple files share overlapping concerns (damage calculation, AI targeting, loot distribution) with no cohesive seam. The deletion test shows that removing a focused file pushes related logic into adjacent files, diluting cohesion.

Solution

Consolidate the combat logic into a single deep module with a small, unified interface (e.g., InitializeCombatState, ApplyDamageWithLogs, CalculateLoot). Introduce an adapter for the simulation engine so tests can run deterministic simulations without real game state.

Wins

  • Deterministic simulation enables faster, repeatable tests.
  • Clearer ownership of combat concepts reduces cognitive load.
  • Leverage grows as the same combat primitives can be reused across PVP, PvE, and auto‑combat.

Recommendation

Strong Consolidate the combat system into one deep module with a focused interface and an adapter for the simulation engine.

Top Recommendation

Deepen the Player Auth Pipeline first.

The handlers are the most prominent shallow modules: they have tiny interfaces but massive, tangled implementations. Extracting validation, DB access, and gameplay logic into testable modules behind a single seam will immediately improve testability, reduce coupling, and enable safer refactoring of the authentication flow.
